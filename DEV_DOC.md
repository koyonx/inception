Each service follows the same shape: `Dockerfile` + `conf/` (configuration
copied into the image) + `tools/` (the entrypoint script).

## 2. Setting up the environment from scratch

### Prerequisites

Inside the virtual machine (Debian or any Linux with a recent Docker):

```sh
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-plugin make openssl
sudo usermod -aG docker $USER      # then log out and back in
docker compose version             # v2 is required (`docker compose`, not `docker-compose`)
```

The host needs roughly 2 GB of free disk for the images and the data.

### Bootstrap

```sh
git clone <this-repo> inception && cd inception
make setup
make hosts
```

`make setup` performs three idempotent steps:

1. **`dirs`** — creates `/home/kkuramot/data/{mariadb,wordpress}`.
   The named volumes are bind-backed to these folders, and Docker refuses to
   create a volume whose `device` does not exist, so this must run first.
2. **`env`** — copies `srcs/.env.example` to `srcs/.env`, replacing
   `__LOGIN__` with the login. An existing `srcs/.env` is never overwritten.
3. **`secrets`** — generates the three files in `secrets/` with
   `openssl rand`, `chmod 600`, only when they do not exist yet.

`LOGIN` is defined at the top of the `Makefile` (`LOGIN ?= kkuramot`) and is
the single knob that decides the domain name (`kkuramot.42.fr`) and the data
path (`/home/kkuramot/data`). Override it with `make LOGIN=wil` if needed.

### Configuration files

| File                | Purpose | Committed? |
|---------------------|---------|------------|
| `srcs/.env.example` | template, documents every variable | yes |
| `srcs/.env`         | actual configuration, read by compose and injected via `env_file` | **no** |
| `secrets/*.txt`     | passwords, mounted at `/run/secrets/<name>` | **no** |

Rule of thumb: if a value would be embarrassing in a `git log`, it goes to
`secrets/`. Everything else goes to `.env`.

## 3. Building and launching

```sh
make            # setup + docker compose up --build -d
make build      # build the images without starting anything
make re         # fclean + full rebuild
```

Under the hood every target calls:

```sh
docker compose -p inception -f srcs/docker-compose.yml --env-file srcs/.env <cmd>
```

### Boot order

`wordpress` declares `depends_on: mariadb: condition: service_healthy`, and
MariaDB's healthcheck is a real `mariadb-admin ping`. On top of that, the
WordPress entrypoint retries the connection 30 times (2 s apart) before giving
up — a bounded loop, never `while true`. `nginx` starts after `wordpress`.

### What each entrypoint does

| Service | First run | Every run | PID 1 |
|---------|-----------|-----------|-------|
| `mariadb` | `mariadb-install-db`, then `mariadbd --bootstrap` with the SQL creating the database and the user | nothing | `mariadbd` |
| `wordpress` | `wp core download`, `wp config create`, `wp core install`, `wp user create` | `chown` the volume | `php-fpm8.2 -F` |
| `nginx` | generate the self-signed certificate | render the vhost with `envsubst`, `nginx -t` | `nginx -g "daemon off;"` |

All of them end with `exec`, so the service is PID 1 and gets `SIGTERM`
directly. No `tail -f`, no `sleep infinity`, no `while true`.

## 4. Managing containers and volumes

```sh
# status / logs
make ps
make logs
docker logs -f wordpress

# a shell inside a container
docker exec -it wordpress bash
docker exec -it mariadb   bash

# wp-cli
docker exec -it wordpress wp --allow-root --path=/var/www/html user list
docker exec -it wordpress wp --allow-root --path=/var/www/html plugin list

# SQL client (see the gotcha about MYSQL_HOST in §7)
docker exec -it mariadb mariadb -h localhost --protocol=socket \
    -u root -p"$(cat secrets/db_root_password.txt)"

# rebuild a single service
docker compose -p inception -f srcs/docker-compose.yml --env-file srcs/.env \
    up -d --build nginx

# check the nginx configuration that was actually rendered
docker exec -it nginx cat /etc/nginx/conf.d/default.conf
docker exec -it nginx nginx -t

# volumes
docker volume ls
docker volume inspect wordpress
```

### Cleaning levels

| Target   | Containers | Images | Volumes | `/home/kkuramot/data` |
|----------|:----------:|:------:|:-------:|:--------------------:|
| `down`   | removed    | kept   | kept    | kept                 |
| `clean`  | removed    | removed| kept    | kept                 |
| `fclean` | removed    | removed| removed | **deleted**          |
| `prune`  | removed    | removed| removed | **deleted** + `docker system prune -af` |

## 5. Where the data lives, and how it persists

Two named volumes, both declared with the `local` driver and bind-backed to
the host folder the subject requires:

```yaml
volumes:
  wordpress:
    name: wordpress
    driver: local
    driver_opts:
      type: none
      o: bind
      device: ${DATA_PATH}/wordpress
```

| Volume      | Mounted at                   | Holds                              | Host path |
|-------------|------------------------------|------------------------------------|-----------|
| `mariadb`   | `mariadb:/var/lib/mysql`     | the whole database                 | `/home/kkuramot/data/mariadb` |
| `wordpress` | `wordpress:/var/www/html` (and `nginx:…:ro`) | WordPress core, themes, plugins, uploads | `/home/kkuramot/data/wordpress` |

They are *named volumes*, not bind mounts: services reference them by name,
`docker volume inspect` describes them, and `docker compose down` does not
remove them. Only their backing storage is pinned to `/home/kkuramot/data`.

Persistence comes from the entrypoints being idempotent: MariaDB skips its
initialisation when `/var/lib/mysql/mysql` exists, WordPress skips its install
when `wp-config.php` exists. So:

```sh
make down && make     # same site, same database, same users
make fclean && make   # everything wiped, fresh install
```

## 6. Things to keep in mind when modifying the project

* **Never commit a credential.** `secrets/*.txt` and `srcs/.env` are in
  `.gitignore`; check with `git status` before every commit.
* **Never use the `latest` tag**, in a `FROM` or in an `image:`. The images of
  this project are tagged `<service>:inception`.
* **Never start a service with a loop.** If a container needs to wait for
  another, use a healthcheck plus a bounded retry.
* **`network: host`, `--link` and `links:` are forbidden** — the `networks:`
  section must stay in `docker-compose.yml`.
* **nginx stays the only published entrypoint**: port 443 only, TLSv1.2/TLSv1.3
  only.
* After touching a `Dockerfile` or a `conf/` file, rebuild that service —
  `up -d --build <service>` — because the configuration is *copied* into the
  image, not mounted.

## 7. Gotchas met while building this, and how they are solved

**A Debian package can pre-fill a directory that a volume is mounted on.**
`apt-get install mariadb-server` already creates the system tables in
`/var/lib/mysql`. When Docker mounts an *empty* volume there, it copies the
image content into it — so the entrypoint saw a populated data directory and
skipped the initialisation, leaving the project without its database and its
user. The mariadb `Dockerfile` therefore ends with `rm -rf /var/lib/mysql/*`.
The nginx image does the same with `/var/www/html/*`, which otherwise seeded
the WordPress volume with the Debian placeholder page.

**The MySQL client reads `MYSQL_HOST` from the environment.** Because
`env_file` injects `MYSQL_HOST=mariadb` into the container, running
`docker exec mariadb mariadb -u root -p…` connects over TCP to itself and is
refused (`root` only exists as `root@localhost`). Pass the host explicitly:

```sh
docker exec -it mariadb mariadb -h localhost --protocol=socket -u root -p"$(cat secrets/db_root_password.txt)"
```

**nginx 1.22 (bookworm) has no `http2 on;` directive.** HTTP/2 is enabled the
old way, as a `listen` parameter: `listen 443 ssl http2;`.

**envsubst would eat the nginx variables.** `envsubst` is called with an
explicit list — `envsubst '${DOMAIN_NAME}'` — otherwise `$uri`, `$host` and
`$args` are replaced by empty strings.

**wp-cli evaluates `--extra-php` twice.** The constants written into
`wp-config.php` are guarded with `defined(...) or define(...)`, otherwise
every wp-cli call prints `Constant already defined`.
